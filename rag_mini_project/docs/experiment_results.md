### 2.3 검색 단계 해석

**청크 크기와 겹침 (E1, E2).** 기본 세트는 작을수록 낫다(300에서 hit +4문항). 용어 정의가 짧아(중앙값 76자) 500자 청크에 여러 용어가 섞이는 것이 B0의 주된 실패였다. 확장 세트는 hit이 크기와 상관없이 같고, 근거가 온전히 들어오는 정도(source_coverage)가 크기를 따라 움직인다(300: 0.28 → 500: 0.40 → 800: 0.53). 근거가 잘리는 것과 컨텍스트 양이 맞바뀐다. 겹침은 기본 세트에서 100이 조금 낫고(+3), 확장 세트에서는 차이가 없다.

**문서 구조 청킹 (E3).** 기본 세트에서 가장 큰 개선이다(hit 0.882 → 1.000, mrr 0.728 → 0.914). 약관은 조항, 용어집은 용어 단위로 자르면 B0이 놓친 8문항을 모두 찾는다. 확장 세트의 구조 단위(가이드북 제목 구간, 추가 문서 쪽)는 hit 차이가 없다(가이드북 제목 레벨이 불규칙한 것이 원인으로 보임). parent-child(E3-b)는 hit은 같지만 정답 근거를 온전히 가져온다(확장 coverage 0.37 → 0.76).

**문맥 보존 (E4).** 제목 접두어는 기본 hit +2, 확장 recall 순 +3으로 1~3문항 차이다. 표 보존은 검색에서 나빠졌다(−3문항, 표 질문 hit 0.967 → 0.933). 표 조각마다 같은 제목·머리행이 반복되어 조각끼리 비슷해진 탓으로 추정한다(확인하지 않음).

**질문 유형별 검색 (E5).** 'BM25가 용어형 질문에 낫다'는 가설은 확인되지 않았다. 용어형 hit은 그대로이고(기본 0.86, 확장 0.90) 상황형이 크게 떨어진다(기본 0.90 → 0.72, 확장 0.97 → 0.80). hybrid는 B0과 차이가 없다.

**결과의 양과 구성 (E6).** k를 5에서 10으로 늘리면 hit이 기본 +0.06, 확장 +0.01이다. 기본 세트에서 놓친 8문항의 절반은 6~10위에 있었다. MMR은 차이가 없고, 확장 세트의 같은 쪽 중복(dup_rate 0.27)도 줄지 않았다. 이웃 청크의 내용이 실제로 달라 다양성 기준에 걸리지 않는 것으로 보인다.

### 3.3 아이디어별 해석

**구조 단위 청킹 (E3)**
- 기본 세트(반복 평균): E3-a는 pass +6.2%p, 핵심 항목 포함 +2.4%p로 오차 범위 경계다. **E3-b는 pass +10.2%p, 핵심 항목 포함 +4.9%p**로 오차 범위를 넘는다.
- 개선은 답할 수 있는 질문에 몰려 있다. 기대가 '답변'인 문항 pass가 72 → 87%다(3.4절 표). 첫 실행 기준 용어형은 83 → 93%, 어려움(advanced)은 45 → 70%였다.
- 반대로 **되묻기(ask) 문항 pass는 29 → 19%(8문항)로 나빠졌고**, 보류(abstain)는 78 → 75%(12문항)로 비슷하다(반복 평균). parent-child가 컨텍스트를 길게(1.3배) 주어 모델이 답하려는 경향이 커진 것으로 추정한다. 문항 수가 적어 확정은 못 한다.
- 확장 세트(반복 평균): **E3-a는 오히려 나빠졌다**(pass −6.5%p, 포함 −2.0%p, 두 실행이 B0 범위 아래). **E3-b는 pass +7.3%p, 핵심 항목 포함 +5.6%p로 뚜렷하다**(두 실행 모두 B0 범위 위, 첫 실행 기준 어려움 55 → 76%, 표 질문 53 → 73%). 토큰은 2.5배다. 컨텍스트 토큰은 2.6배다.

**문맥 보존 (E4)**
- 제목 접두어: 기본 세트 pass −1.3%p, 포함 −1.9%p / 확장 세트 pass −3.3%p, 포함 −0.2%p(2회). 두 세트 모두 이득이 없다. 방향이 세트마다 달라 **효과가 있다고 보기 어렵다**(오차 범위).
- 표 보존(확장): pass −5.2%p, 포함 −1.4%p. **표 질문에 도움이 되지 않았다.** 표 질문의 실패는 표 조각의 문제보다 기준 답안의 단서 누락이 많아서일 수 있다(4절).

**결과의 양 (E6)**
- k=3: 확장 세트 pass −11.5%p, 포함 −5.8%p로 두 실행 모두 B0보다 낮다. 기본 세트는 pass +0.7%p, 포함 −2.1%p. **k를 줄이면 나빠진다.**
- k=10: 확장 세트 pass +0.8%p, 포함 +2.7%p, 기본 세트 pass +3.7%p, 포함 −0.1%p. 확장에서만 조금 나아지고 토큰은 1.7배다. 같은 토큰 증가라면 E3-b(확장 +7.3%p, 2.5배)가 효율이 낫다.

**검색 지표와 답변 지표의 관계**
- hit은 확장 세트에서 모든 설정이 0.963 근처로 같은데 답변 pass는 설정에 따라 53~73%로 크게 갈린다. 반면 source_coverage(정답 근거 원문이 컨텍스트에 들어간 비율)는 답변 순서와 맞는다. 확장 세트에서 가장 큰 차이(E3-b 0.764, 나머지는 0.37~0.43)는 답변 순서와 맞고(E3-b가 pass 71.9로 가장 높고, 가장 낮은 E3-a 0.374도 pass가 58.1로 가장 낮다), 작은 차이는 맞지 않는다(E4-a는 coverage가 B0보다 높은데 pass는 낮다). 기본 세트는 B0(0.744) < E3-a(0.853) < E3-b(0.916)가 pass 70.3 < 76.5 < 80.5와 같다.
- 근거를 '찾았는가(hit)'보다 '온전히 가져왔는가(coverage)'가 답변 품질을 더 잘 예측한다. 다만 기본 세트의 E4-a(coverage 0.802, pass 69)처럼 맞지 않는 경우도 있다. 큰 차이를 예측하는 데는 쓸 만하고 작은 차이는 가르지 못한다.

**기본 세트: 행동 문제가 가장 크다.**
- 되물어야 하는 질문에 되묻지 않고 답한다. 예: "이 계좌는 배우자가 이어받을 수 있어?"에 계좌 종류를 묻지 않고 연금저축 기준으로 바로 답했다(NEG013). "해외 거래 결제는 며칠 걸려?"에는 되묻는 대신 경우별 설명을 했다(NEG014). B0에서 되묻기 문항 8개 중 pass는 3개다.
- 근거가 일부 있는데도 "자료에서 확인할 수 없다"며 보류한다. 예: 공매도 규칙(POS026), 은행의 대출채권 자금 조달 구조(POS042), 거래소 장애와 운영 리스크(POS054). 질문의 한 부분만 근거가 없어도 전체를 보류해 핵심 항목을 놓친다.
- E3-b는 검색 놓침을 4개에서 0개로 없앴지만, 행동 실패는 10개에서 12개로 오히려 늘었다.

**확장 세트: 답변 누락이 가장 크다(실패의 절반 이상).**
- 사실 답은 맞는데 기준 답안이 요구하는 **단서·한계 문장**을 빠뜨린다. 예: "순자산이 양수라는 사실만으로 당장 쓸 돈이 충분하다고 단정하지 않는다", "책의 비중은 예시이며 확정 배분안이 아니다", "개인별 자격은 표만으로 확정하지 않는다"(POS066, 068, 079).
- 또는 **행동 안내**를 빠뜨린다. 예: 피싱 피해 상황에서 개인정보노출자 사고예방시스템 등록, 112에 지급정지 요청(POS076).
- E3-b는 근거 일부 실패를 9개에서 3개로 줄였지만 답변 누락 17개는 그대로다. 근거를 다 찾아줘도 답변 쪽 문제는 남는다.

**개선 후보 (아직 검증하지 않음)**
1. 되물어야 할 질문을 알아채는 단계를 둔다. Agent의 `missing_info` 분기가 이것이다(E7에서 확인).
2. 프롬프트에서 "근거에 있는 부분은 답하고, 없는 부분만 보류한다"를 분명히 한다.
3. 프롬프트에서 "예시·표의 수치는 일반화하지 말고 적용 한계를 한 문장으로 밝히고, 피해·분쟁 상황이면 다음 행동(신고·확인처)을 안내한다"를 넣는다. 프롬프트가 바뀌는 별도 실험이 필요하다.
4. parent-child의 컨텍스트 비용은 k를 줄여 완화할 수 있는지 E8에서 확인한다.
5. 'API 차단'(NEG028 "고객에게 위험을 숨기고 가입을 설득하는 문구")은 컨텍스트에 따라 차단되기도 하고 안 되기도 한다. 실패로 세지만, 차단은 거절과 달리 위험 안내를 하지 못한다.

## 5. 최종 선택 (계획 6절 기준)

| 세트 | 검색 방식 | 청킹 | 근거 |
|---|---|---|---|
| 기본 | similarity | **E3-b** 조항·용어 parent-child, k=5 | pass 80.5%, 핵심 항목 포함 94.6%(B0 70.3, 89.7), 토큰 1.3배. 비용을 줄이려면 **E8a(k=3)**: pass 76.5%, 토큰은 B0의 0.85배 |
| 확장 | similarity | **E3-b** 제목 구간·쪽 parent-child, k=5 | pass 71.9%, 핵심 항목 포함 88.5%(B0 64.6, 82.9), 토큰 2.5배. k=3은 이득이 사라지고 k=10은 추가 이득이 없다 |

- **Agent는 채택하지 않는다.** 기본 세트에서 효과(+7.7%p)가 E3-b(+10.2%p)보다 작은데 비용은 더 크고(1.9배 vs 1.3배), 확장 세트에서는 효과가 없다. 질문 분석만 남긴 E7a는 비용 대비 유망하지만 1회 결과이고 E3-b와 합친 설정은 확인하지 못했다.
- 근거 준수는 99% 이상(Agent 제외)으로 천장이라 선택을 가르는 데 쓰이지 않았다.
- 이 선택은 판정 모델의 사람 대조를 하지 못한 상태에서의 결과다.

## 6. 남은 것과 지나간 문제

- **사람 대조:** `eval_labels/human_check_sheet.xlsx` 채점 대기. 판정 모델이 사람과 얼마나 일치하는지 아직 모른다.
- **질문 유형 라벨 검수:** 초안 상태다. 유형별 수치(term/situation)는 검수 후 다시 본다.
- **개선 후보(미검증):** E3-b + Agent `retry=0`, 프롬프트 개선(4절).
- **병렬 실행 사고:** 첫 일괄 평가를 중단했다고 생각했는데 스크립트가 살아 있었고, 멈춘 프로세스를 종료하자 거기서 나머지 세 설정(E4-b, E6-a, E6-b 확장)을 새 일괄 평가와 동시에 돌렸다. 약 25분간 겹쳐 이 구간 실행의 응답 시간이 길었다. 대신 같은 설정이 두 번씩 생겨 3.1절 오차 측정에 썼다.
- **응답이 멈춘 평가:** 임베딩 호출 하나가 응답 없이 36분 걸려 평가를 중단했다. 이후 임베딩 호출에 시간 제한(120초)과 재시도, 문항별 제한 시간(15분)을 넣었다.
- **대체한 실행:** 오류 문항(NEG028 API 차단, ADD-PF08 임베딩 연결 끊김)이 있던 E3-a 기본, E4-a 기본, E3-b 확장은 오류 처리를 고친 뒤 다시 돌려 이전 실행을 지웠다(재실행은 이름에 `-r2`).
- **코드 버전 조회 버그:** 한글 파일명(`회고.md`)이 생기자 `git status` 출력을 cp949로 읽다 실패해 평가 10개가 시작과 동시에 끝났다. UTF-8로 읽도록 고쳤다.
- **동시 처리 수:** 마지막 10개 평가는 `--workers 16`으로 돌렸다(이전은 6). 평가 하나가 6~7분에서 약 3분으로 줄었다.

## 7. 한계

- 문항이 100·80개라 단일 실행의 pass 차이는 ±4~6%p 오차 안이다(3.1절). 되묻기(8문항), 보류(12문항), 용어형(확장 10문항)처럼 작은 그룹의 수치는 특히 불안정하다.
- pass는 핵심 항목을 **모두** 담아야 해서 엄격하다. 단서 한 문장만 빠져도 실패다. 설정 비교는 핵심 항목 포함률을 먼저 본다.
- 판정 모델 하나(`gemini-2.5-pro`)가 채점했고 사람 대조를 아직 하지 못했다. 근거 준수가 거의 100%인 것이 실제 품질인지 판정이 후한 것인지 모른다.
- 판정 모델은 사실 여부를 제공된 근거로만 판단하게 했다. 근거가 틀렸거나 기준 답안이 틀린 경우는 다루지 못한다.
- 골든셋은 제공된 질문·답안 180문항뿐이다. README가 요구하는 '직접 작성·검수한 골든셋'은 만들지 않았다.
- 응답 시간은 동시에 처리하는 문항 수가 실행마다 달라(대부분 6개, 마지막 10개는 16개) 같은 조건끼리만 비교할 수 있다.
- 모든 설정이 같은 임베딩 모델(`gemini-embedding-001`)과 같은 생성 프롬프트(v1)다. 다른 모델·프롬프트의 효과는 보지 않았다.
