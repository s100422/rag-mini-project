## 0. 먼저 읽을 것: 이 비교의 한계

1. **`gemini-embedding-2`는 `task_type`을 반영하지 않는다(확인함).** 같은 문장을 `RETRIEVAL_QUERY`와 `RETRIEVAL_DOCUMENT`로 임베딩하면 001은 코사인 0.885로 다르지만 002는 1.000으로 완전히 같다. 이 프로젝트는 문서 `RETRIEVAL_DOCUMENT`, 질의 `RETRIEVAL_QUERY`를 쓰는데(`rag/chroma_store.py`) 002에서는 이 구분이 사라진다. 002는 질의·문서를 텍스트 앞의 지시문(task 접두어)으로 구분하는 방식이라, **아래 결과는 '모델만 바꾸고 접두어 없이 쓴' 경우의 값**이다. 002의 최대 성능이 아니다. 접두어를 넣은 재실험은 하지 않았다.
2. 답변 단계는 같은 설정을 다시 돌려도 pass가 5%p, 핵심 항목 포함이 3%p 안팎으로 흔들린다(원본 3.1절). 이 기준 안쪽 차이는 '차이 없음'이다. 002에서 1회만 돌린 설정(E4-a 기본, E6-a·b 기본, E7a·b 등)은 특히 조심해서 읽는다.
3. 검색 단계는 BM25(E5-a)가 임베딩을 쓰지 않아 두 실행의 값이 정확히 같다. 파이프라인이 같다는 대조군이다.

## 1. 한눈에 보는 결론

1. **모델만 바꾸면 전반적으로 나빠졌다.** 기준 B0 기본 세트 hit@5 0.882 → 0.691, pass 70.3 → 63.3%, 핵심 항목 포함 89.7 → 80.9%(기준 밖 차이). 확장 세트는 hit@5 0.963 → 0.950, pass 64.6 → 60.4%, 포함 82.9 → 79.8%로 오차 경계 근처다. 위 0절 1번(task 접두어 없음)이 원인의 일부일 수 있으나 이번 실험으로는 가르지 못했다.
2. **'청킹이 가장 크다'는 결론은 유지되고 더 뚜렷해졌다.** 구조 단위 청킹은 임베딩이 바뀌어도 검색이 거의 그대로다(기본 세트 hit@5 1.000 → 0.985). Recursive 계열은 크게 무너졌다(B0 0.691, 크기 800은 0.515). 그 결과 B0 대비 E3-b의 개선폭이 기본 세트 pass +10.2 → +15.7%p, 확장 세트 +7.3 → +8.3%p로 커졌다. E3-b 자체 점수는 거의 같다(기본 80.5 → 79.0, 확장 71.9 → 68.8, 모두 오차 안).
3. **Agent는 채택하지 않는다는 결론이 더 강해졌다.** 기본 세트에서 E7이 B0와 같아졌다(pass 63.3 vs 63.5, 원본은 +7.7%p). 확장 세트도 효과가 없다(60.4 vs 59.4). 토큰은 기본 세트 2.1배, 확장 2.3배다.
4. **검색 방식·제목 접두어·표 보존은 여전히 이득이 없다.** 제목 접두어는 검색이 더 나빠졌고(hit@5 기본 −0.24, 확장 −0.08), 답변은 B0 대비 차이 없음 범위다(pass 기본 −1.3, 확장 +2.7%p). 표 보존은 확장 세트에서 차이 없음이다.
5. **k는 002에서 효과가 더 컸다.** k=3은 기본 세트 52.0%(B0 63.3)로 나빠졌고(1회), 확장도 52.5%다. k=10은 확장 72.5%(B0 60.4, 1회)다. parent-child(E3-b) 위에서 k=10(E8b)은 기본 85.0%로 E3-b(79.0)보다 6.0%p 높고(포함은 +2.9%p로 경계), 확장은 73.1%로 E3-b(68.8)보다 4.3%p 높다. 원본에서는 둘 다 '추가 이득 없음'이었다. 토큰은 1.8~1.9배다.
6. **근거 준수가 약간 떨어졌다.** E3-b 기본 세트 99.5 → 97.2%, E8b 99.7 → 97.8%. Agent를 뺀 나머지는 98% 안팎 이상이다(Agent는 원본과 같이 89~99%).

## 3. 실행 중 있었던 일 (기록 정직성)
