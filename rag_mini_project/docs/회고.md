# 회고

2026-10-21 작성. 평가 10개가 남은 중간 회고다(`docs/progress.md`).

## 1. 잘 된 것

- 기준(B0)을 먼저 정하고 한 요소만 바꿔서, 결과 차이를 원인 하나에 연결할 수 있었다.
- 같은 설정을 반복해 평가 오차(pass ±4~6%p)를 쟀고, 그 안쪽 차이를 효과로 착각하지 않았다.
- 기록을 실험 ID로 연결하고 기준 대비 바뀐 설정을 자동으로 남겼다.

## 2. 문제점과 개선 방안

### 2.1 실행 시간이 오래 걸림

- **문제:** 답변 평가 한 번이 약 7분이다. 처음 13개 설정이 약 2시간 40분 걸렸고, 남은 10개도 순차로 약 70분이다.
- **원인:** 시간 대부분이 판정 모델 대기다(문항당 약 17초, 검색 1.5초·생성 4초). 문항을 6개씩만 동시에 처리하고 평가는 순서대로 돌렸다.
- **해 본 것:** 평가를 세 줄로 나눠 동시에 실행했다. 실행당 시간이 거의 늘지 않았다(약 7.4분 → 약 8분).
- **개선 방법:** 동시 처리 수를 6 → 16(`--workers 16`)으로 올리고 세 줄로 나눠 동시에 실행한다. 병목이 API 응답 대기라 동시 수에 비례해 빨라진다. 남은 10개가 70분 → 10~25분일 것으로 본다(추정, 아직 실행해 보지 않음).
- **고르지 않은 방법:** asyncio(대기가 병목이라 스레드와 효과가 같음), Gemini Batch API(결과가 수 시간 걸릴 수 있음, 확인하지 않음), 판정 모델의 생각 줄이기(이전 실험과 채점 기준이 달라짐).

### 2.2 그 밖의 문제

| 문제 | 원인 → 개선 |
|---|---|
| Chroma가 1,000개 넘는 컬렉션의 인덱스를 못 씀 | 경로에 한글이 있어서 → 한글 없는 경로로 이동 |
| 같은 설정인데 MMR 지표가 실행마다 달랐음 | 검색 탐색 폭이 작아서 → `ef_search`를 1000으로 |
| 동시 호출 중 `client has been closed` | 모델 클라이언트가 둘 생겨서 → 생성에 잠금 |
| LangSmith 월 한도 초과(429) | 문항 전체를 추적해서 → `LANGSMITH_TRACING=false` |
| 쪽 수가 3쪽·74쪽으로 잘못 잡힘 | `(printed 82)`가 붙은 쪽 표시를 놓쳐서 → 정규식 수정 |

## 3. 다음에 다르게 할 것

1. 평가 전에 총 소요 시간(설정 수 × 실행당 시간 ÷ 동시 수)을 계산하고, 판정처럼 느린 호출에 맞춰 동시 수를 높게 잡는다.
2. 외부 API 호출에는 처음부터 시간 제한과 재시도를 넣고, 일괄 실행에는 멈춤 감시를 건다.
3. 결과를 단일 실행으로 결론 내지 않고, 판정 모델의 사람 대조는 평가와 같은 시기에 한다.
