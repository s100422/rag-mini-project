# RAG 실험 계획

기록 형식은 `docs/experiment_records.md`를 따른다. 모든 비교 실험은 `--baseline <기준 실험 ID>`로 돌려
`config.json`의 `changes`에 **바꾼 요소 하나만** 잡히는지 확인한다.

**진행 현황과 결과는 `docs/experiment_results.md`에 있다.** **계획한 평가를 모두 마쳤다**(검색 단계, 답변 단계, 합친 설정 E8, Agent E7, 반복 포함). 남은 것은 `docs/progress.md`에 있다.

## 1. 질문 세트와 검색 대상

검색 범위가 다른 세트를 따로 평가한다. 세트끼리는 지표를 비교하지 않는다.

| 세트 | 검색 대상 PDF | 평가 문항 | 비고 |
|---|---|---|---|
| 기본 세트 | 용어집 1개 + 표준약관 15개 | 검색: 68개(positive 60 + 근거가 있는 negative 8)<br>답변: 100개(positive 60 + negative 40) | negative의 '자료에 없음' 판단은 이 범위 기준(README) |
| 확장 세트 | 금융생활 가이드북 1개 + 추가 문서 6개 | 검색·답변: 80개(가이드북 20 + 추가 문서 60) | |

- 근거가 없는 negative 32개는 검색 지표가 없다. 답변 단계(확인·보류·거절)에서만 평가한다.
- 질문 유형 라벨은 `eval_labels/question_types.csv`에 있다(초안, **검수 중**).
  - `question_type`: term(용어·제도·조항·표 이름을 직접 묻는 질문) / situation(상황을 풀어 설명한 질문)
  - `needs_table`: 표·그래프 수치를 읽어야 답할 수 있는 질문
  - 분포: 기본 세트 term 29 / situation 39, 확장 세트 term 10 / situation 70, 표 질문 30(확장 세트)
  - 확장 세트의 term은 10문항뿐이라 질문 유형별 비교(E5)는 **기본 세트를 주 근거**로 쓰고, 확장 세트는 참고로만 본다.

README가 요구하는 필수 비교는 청킹 전략, 검색 전략, 기본 RAG와 Agent 세 가지다. 그 안에서 어떤 실험이 필요한지는
아래 문서 특성과 예비 실행에서 본 실패로 고른다. B0 결과의 실패 분석(5절 2단계)으로 우선순위를 다시 확인한다.

| 근거 | 관찰 | 고른 실험 |
|---|---|---|
| 약관 조항 길이가 들쭉날쭉(중앙값 281자, 상위 10% 951자, 최대 5,450자) | 고정 크기로 자르면 긴 조항은 잘리고, 짧은 조항은 다른 조항과 섞인다 | E1(크기), E3(조항 단위) |
| 용어집 정의가 짧음(중앙값 76자, 500자 넘는 것 1개) | Recursive 500이면 한 청크에 용어 여러 개가 섞여 불필요한 내용이 같이 검색된다 | E3(용어 단위), E1-a(300) |
| 가이드북·추가 문서에 표·그래프가 많음(표 블록 약 190개, 표 질문 30개) | 표가 잘리면 단위·머리행이 떨어져 나간다 | E4-b(표 보존) |
| 가이드북 제목 레벨이 불규칙 | 제목만으로는 단위를 나누기 어렵다 | E3-a(제목·문단 단위, 파서 필요) |
| 예비 실행: 쪽 단위 확장 세트의 source_coverage@5가 0.39 | 정답 쪽이 걸려도 그 쪽 원문은 일부만 컨텍스트에 들어간다 | E1(크기), E2(겹침), E3-b(parent) |
| 예비 실행: 같은 쪽 청크가 상위 5개에 중복(320건 중 202건) | 중복이 k 자리를 차지해 다른 근거가 밀려난다 | E6-c(MMR), E6(k) |
| 예비 실행: BM25 hit@5가 용어형 0.93, 상황형 0.72 | 질문 유형에 따라 맞는 검색 방식이 다르다 | E5(BM25·hybrid) |
| 예비 실행: 기본 세트 advanced 난이도 recall@5가 0.66~0.71(similarity·mmr·hybrid, 다른 난이도는 0.90 이상) | 근거가 여러 개인 복합 질문에서 일부 근거를 놓친다 | E6(k 10), E7(Agent 재검색) |

## 3. 기준 설정 (B0)

| 항목 | 값 |
|---|---|
| 청킹 | **일반 Recursive 500/50**. 문서 구조(조항·용어·제목)를 쓰지 않고 문서 본문 전체를 자른다. parent 없음. 제목·문맥 접두어 없음 |
| 분할 기준 | `["\n\n", "\n", ". ", " ", ""]`, 쪽 표시는 본문에서 빼고 쪽 위치만 기록 |
| 임베딩 | `models/gemini-embedding-001` |
| 검색 | similarity(코사인), **k = 5**(컨텍스트에 넣는 개수), HNSW ef_search 1000(전수 검색과 같음) |
| 결과 단위 | 청크 1개 = 컨텍스트 1자리 |
| 답변 생성 | `gemini-3.8-flash`(응답에 찍힌 버전 기록), temperature 0, 생각(thinking) 끔, 프롬프트 v1 |
| 평가 | 같은 질문 세트, k ∈ {1, 3, 5, 10}에서 검색 지표 계산, 대표 지표는 k=5. 답변 판정 모델·프롬프트 고정(4.2절) |

B0은 세트마다 하나씩 만든다: `base_rec_c500_o50`(용어집+약관), `extended_rec_c500_o50`(가이드북+추가 문서).
컬렉션은 `python -m rag.build_index --strategy recursive|structure|parent-child [--title-prefix] [--table-aware]`로 만든다.
전략과 설정은 컬렉션 메타데이터에 남고, 평가가 이것을 `settings.chunking`으로 읽는다.
지금 있는 `base_c350_o50`(조항·용어 parent-child 350/50)과 `extended_c500_o50`(쪽 단위 500/50)은 예비 실행이다.

**근거 경계를 넘는 청크의 채점 규칙(B0, E1, E2):** 문서 전체를 자르면 청크 하나가 조항·용어·쪽 여러 개에 걸칠 수 있다.
청크에는 걸친 근거 ID를 모두 기록한다(`source_ids`).
- 그중 하나라도 정답이면 그 자리는 정답으로 센다(hit·precision).
- 청크가 덮은 정답 ID는 모두 찾은 것으로 센다(recall).
- 앞 자리들에서 이미 나온 근거 ID로만 이루어진 청크는 중복으로 센다(dup_rate).

## 4. 지표

### 4.1 검색 지표 (모든 실험)

| 지표 | 무엇을 보나 | 측정 방법 |
|---|---|---|
| hit@k, recall@k, all_hit@k, mrr | 필요한 근거가 컨텍스트에 들어왔는가 | 상위 k개 결과의 근거 ID와 정답 근거 ID 비교 |
| precision@k, dup_rate@k | 불필요하거나 중복된 결과가 얼마나 섞였나 | 자리 단위 정답 비율, 이미 나온 근거만 담은 자리 비율 |
| context_chars@k | 컨텍스트 양(답변 비용·잡음) | 상위 k개 원문 글자 수 |
| source_coverage@k | 근거가 잘렸는가 | 정답 근거 원문 중 컨텍스트에 들어간 글자 비율(줄 단위 매칭) |
| key_phrase_recall@k | 핵심 구절이 들어왔는가(기본 세트만) | must_include 중 원문에 그대로 있는 구절의 포함률 |
| 검색 시간 | 검색 비용 | 질의 1회 시간(p50·p95) |

### 4.2 답변 지표 (RAG·Agent 단계, E4·E7과 최종 설정)

| 지표 | 무엇을 보나 | 측정 방법 |
|---|---|---|
| 답변 정확도 | 기준 답안의 핵심 내용을 담았는가 | must_include 항목마다 판정 모델이 '의미상 포함'을 0/1로 판정 → 포함 비율. 문자열 포함 여부도 보조로 기록 |
| 금지 내용 | 하면 안 되는 말을 했는가 | must_not_include 항목마다 판정 모델이 위반 여부 0/1 → 위반 문항 비율 |
| 근거 준수 | 답변이 컨텍스트에 근거하는가 | 판정 모델이 답변을 주장 단위로 나눠, 각 주장이 실제로 넣은 컨텍스트로 뒷받침되는지 판정 → 뒷받침 비율, 근거 없는 주장 수 |
| 인용 정확도 | 파일명·쪽을 맞게 달았는가 | 답변의 인용을 근거 ID로 바꿔 규칙으로 채점: 인용이 정답 근거인 비율(정밀도), 정답 근거가 인용된 비율(재현율) |
| 기대 행동 일치 | 답할지·정정할지·확인할지·보류할지·거절할지 | 판정 모델이 답변의 행동을 5가지 중 하나로 분류해 기대 행동과 비교. 기대 행동 22종은 5가지로 묶는다(아래) |
| 응답 시간 | 사용자가 기다리는 시간 | 문항 하나의 검색+생성 시간(p50·p95), 검색·생성 분리. 문항 6개를 동시에 처리하는 조건에서 잰 값이라 절대값보다 실험 간 상대 비교용이다(판정 시간은 제외) |
| 사용량 | 자원 | 모델 호출 수, 검색 횟수, 입력·출력 토큰. 문항별로 합산하고 세트 전체 합계·평균을 낸다 |

기대 행동 묶음(판정용):
- 답변: `answer_with_citation`, `ignore_injection_and_answer_with_citation`
- 정정: `correct_*`, `ignore_injection_and_correct_with_citation`
- 확인 질문: `ask_clarifying_question`, `abstain_and_request_context`
- 보류: `abstain_*`(위에 든 것 제외), `require_freshness_check`, `flag_stale_source_and_verify`, `ignore_injection_and_preserve_provenance`
- 거절: `refuse_*`, `ignore_injection_and_refuse_recommendation`

**판정 방법 고정:** 판정 모델(모델 ID·버전)과 판정 프롬프트는 실험 내내 하나로 고정하고 `settings.eval.judge`에 기록한다.
temperature는 0이다. 판정 모델은 `gemini-2.5-pro`로, 생성 모델(`gemini-3.8-flash`)과 달라서 자기 답을 후하게 보는 치우침을 줄인다.
판정 모델은 기대 행동을 보지 못한다. 문항 20개를 사람이 직접 채점해(`eval_labels/human_check_sheet.xlsx`) 판정 모델과의
일치율을 확인한다(`python -m rag.human_sheet compare`).

### 4.3 해석 규칙

- 지표 평균과 함께 **기준 대비 나아진 문항 수 / 나빠진 문항 수**를 같이 보고한다(문항이 68·80개로 적다).
  `python -m rag.compare --baseline-of <실험 ID> ...`가 기준 대비 차이, 나아진/나빠진 문항 수, 그룹별 차이를 보여 준다.
- 순 개선이 1~2문항이면 '차이 없음'으로 본다.
- **반복과 오차(실측):** 같은 설정을 다시 돌리면 pass가 3.4~6.2%p, 핵심 항목 포함률이 0.9~3%p 달라졌다(temperature 0인데도 답변 문장이 매번 다르다, 결과 문서 3.1절). 그래서 답변 단계는 (a) 핵심 항목 포함률을 먼저 보고 pass는 보조로, (b) **pass 5%p, 핵심 항목 포함 3%p 안쪽 차이는 '차이 없음'**, (c) 최종 후보와 기본 RAG·Agent 비교는 2회 이상 돌려 평균과 범위로 비교한다(`python -m rag.report`).
- **API 차단:** 모델 API가 프롬프트를 막으면(`block_reason`, 예: 고객을 속이는 문구 요청) 답변이 없다. 이 문항은 제외하지 않고
  `blocked`로 기록해 실패(pass 0)로 센다. 같은 질문도 컨텍스트에 따라 차단되기도 하고 안 되기도 해서, 요약에 `n_blocked`를 남긴다.
  답변 중 오류(그 밖의 호출 실패)는 `n_errors`로 따로 세고 다시 돌린다.
- 전체 결과와 함께 `question_type`, `needs_table`, `source_doc`, `difficulty`, 기대 행동 그룹별로 본다.

## 5. 비교 실험

각 실험은 B0에서 **한 요소만** 바꾼다. 나머지(질문 세트, 검색 대상, 임베딩, 검색 방식, k, 평가 방법)는 고정한다.

| ID | 아이디어 | 바꾸는 요소 = 값 | 고정 | 판정 지표 | 가설 |
|---|---|---|---|---|---|
| E1-a, E1-b | 청크 크기 | chunk_size = 300, 800 | 겹침 50, k 5 | source_coverage, hit, precision, context_chars | 작으면 근거가 잘리고, 크면 불필요한 내용이 섞인다 |
| E2-a, E2-b | 겹침 | chunk_overlap = 0, 100 | 크기 500, k 5 | source_coverage, hit, dup_rate | 겹침이 없으면 경계에 걸친 근거가 잘린다 |
| E3-a | 문서 구조 청킹 | 분할 단위 = 구조 단위: 용어집은 용어·정의, 약관은 조항, 가이드북은 제목·문단, 추가 문서는 쪽. 단위가 500자를 넘으면 그 안에서 Recursive 500/50 | parent 없음, 검색·k | hit, source_coverage, key_phrase_recall, precision | 근거 단위와 청크 단위가 맞으면 정답이 한 청크에 온전히 담기고 다른 근거가 덜 섞인다 |
| E3-b | 구조 + parent-child | E3-a 단위를 parent로 두고 child 500/50으로 검색, 결과는 parent | 그 밖은 E3-a와 같음 | hit, source_coverage, context_chars | **E3-a 대비** 한 요소(결과 단위) 변경. 컨텍스트가 길어지는 대신 근거가 온전해진다 |
| E4-a | 문맥 보존: 제목 | 청크 앞에 `[문서 제목 > 상위 제목]` 접두어(임베딩·컨텍스트 모두) | 청킹 B0 | **답변 지표**(답변 정확도·근거 준수·인용), 보조로 hit(상황형) | 짧은 청크가 어느 문서·조항인지 알 수 있어 검색과 답변이 나아진다 |
| E4-b | 문맥 보존: 표 | 표는 행 경계에서만 자르고 조각마다 표 제목·머리행·단위·각주를 붙임 | 청킹 B0, 확장 세트만(기본 세트에는 표가 없음) | **답변 지표**(needs_table 그룹의 답변 정확도·수치 정확도), 보조로 source_coverage | 표 조각에 단위·머리행이 붙으면 수치 질문 답이 맞아진다 |
| E5-a, E5-b | 질문 유형별 검색 | method = bm25, hybrid(가중치 0.5) | 청킹 B0, k 5 | question_type별 hit·mrr | 용어형은 BM25, 상황형은 벡터가 낫고 hybrid가 둘을 절충한다 |
| E6-a, E6-b | 결과 양 | k = 3, 10 | 청킹·검색 B0 | hit, precision, dup_rate, context_chars | k가 크면 근거는 더 들어오지만 중복·잡음도 는다. **검색 지표는 B0 실행의 k=3·10 값으로 읽는다**(지금 검색기는 k를 바꿔도 앞 순위가 같다). 따로 돌리는 실험은 답변 단계에서만 한다 |
| E6-c | 결과 구성 | method = mmr(λ 0.5) | k 5 | dup_rate, hit, all_hit(근거 2개 이상 문항) | 같은 쪽 청크 중복이 줄고 여러 근거가 필요한 문항이 나아진다 |
| E7 | Agent 구조 | 기본 RAG → 직접 설계한 Agent | 검색 설정·생성 모델·질문 세트·판정 방법 | 답변 지표, 사용량, 응답 시간 / question_type·기대 행동별 | 여러 요소가 함께 바뀐다(아래) |
| E7a, E7b | Agent 요소별 ablation | E7a: 재검색 끔(`retry=0`), E7b: 질문 분석·분기 끔(`analyze=0,route=0`) | E7과 같음 | 답변 지표, 사용량 | E7 변화의 원인이 어느 요소인지 |
| E8a, E8b | 합친 설정 | **E3-b 대비** k = 3(비용 절감), 10(품질) | E3-b(parent-child), similarity | 핵심 항목 포함, pass, 사용량 | 좋았던 요소(구조 parent-child, k)가 겹쳐도 효과가 유지되는지, 비용을 줄일 수 있는지 |

### E4 해석 규칙

- E4는 '답변이 달라지는지'를 보는 실험이라 판정은 답변 지표로 한다. 검색 지표는 원인을 설명하는 보조 자료다.
- E4-a는 접두어가 임베딩과 컨텍스트에 동시에 들어간다. 효과가 나오면 원인을 가르는 추가 실험 두 개를 돌린다.
  - E4-a1: 임베딩에만 접두어
  - E4-a2: 컨텍스트에만 접두어

### E7 해석 규칙

기본 RAG와 Agent는 여러 요소가 함께 달라진다(질문 분석, 재검색, 근거 판단, 거절·확인 분기, 프롬프트 등).
- `changes`에 달라진 요소를 모두 남기고, 결과는 **전체 구성의 효과**로 해석한다.
- 특정 요소(예: 재검색)가 개선의 원인이라고 보려면 그 요소만 끄거나 켠 Agent 변형을 따로 돌려 확인한다(ablation).
- 검색 설정은 B0으로 고정한다. E1~E6에서 더 나은 설정을 찾았으면 '기본 RAG + 그 설정'과 'Agent + 그 설정'을 한 쌍으로 다시 비교한다.

**자원 대비 품질 분석:**
- 문항마다 모델 호출 수, 검색 횟수, 입력·출력 토큰, 응답 시간을 합산하고, 세트 전체 합계와 문항 평균을 기본 RAG와 나란히 둔다.
- 품질 증가분을 추가 자원으로 나눈 값을 낸다. 예: 답변 정확도 1%p를 올리는 데 든 추가 토큰, 추가 호출 수, 추가 시간.
- 문항을 '나아짐 / 같음 / 나빠짐'으로 나누고 각 묶음의 추가 비용을 본다. 비용만 늘고 품질이 같은 문항이 많으면 그 분기는 불필요하다.
- 질문 유형·기대 행동별로 같은 분석을 해서 Agent가 유리한 질문과 불리한 질문을 정리한다.

## 6. 최종 설정 선택

세트별로 고른다. 기준은 실험 전에 이렇게 정해 둔다.

1. **검색 단계(E1~E6):** hit@5가 높은 설정을 고른다. 차이가 4.3절 기준으로 '차이 없음'이면 source_coverage@5 → context_chars@5(작을수록 좋음) → 검색 시간 순으로 가른다.
2. **답변 단계(E4, 최종 설정):** 답변 정확도와 근거 준수를 함께 본다. 근거 준수가 떨어지면 정확도가 높아도 고르지 않는다. 그다음 기대 행동 일치, 사용량 순으로 본다.
3. **요소 합치기:** 단계별로 좋았던 요소를 합친 설정은 서로 영향을 줄 수 있다. 답변 단계에서 효과가 오차를 넘은 요소는 구조 parent-child(E3-b) 하나뿐이어서, 여기에 k 변경을 겹친 E8로 확인한다. 기준을 E3-b로 두므로 바뀐 요소는 k 하나다.
4. **Agent 채택:** 5절의 자원 대비 품질 분석에서 추가 자원에 비해 품질 개선이 충분한 경우에만 Agent를 최종 구성으로 고른다.

선택 이유는 '어떤 실험의 어떤 지표가 얼마였는지'로 적는다.
